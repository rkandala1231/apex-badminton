Prod never moves. QA turned out to share Dev's Supabase project instead of getting its own — Supabase's free-project cap is per account, not per org, so a third project wasn't available. It's fully isolated at the data level anyway, via its own Postgres schema.

done

QA schema built inside Dev's project

done, verified

A second Postgres schema (qa) alongside Dev's public — its own tables, RLS policies, register_for_apex function, and analytics functions. Verified directly: anon can call the public stats and register, anon cannot read raw rows, admin access works — same safety posture as Prod and Dev.

Expose the qa schema

1 min, you

Open apex‑badminton‑dev in the dashboard → Project Settings → API → Data API → Exposed schemas → add qa next to public → Save. Without this, QA gets a "schema not found" error.

One-time Vercel setup — Dev

can start now

A fresh clone of your repo, checked out to its own branch, linked to its own Vercel project:

git clone https://github.com/rkandala1231/apex-badminton.git apex-badminton-dev
cd apex-badminton-dev
git checkout -b dev && git push -u origin dev
copy ..\apex-react\.env.development .env
npm install
npx vercel login
npx vercel                # project name: apex-badminton-dev
npx vercel env add VITE_SUPABASE_URL production
npx vercel env add VITE_SUPABASE_ANON_KEY production
npx vercel --prod

Part 2

Handing deploys to the agents

Three GitHub Actions jobs run on every push. Set the following up once, and git push becomes the only deploy step you ever type again.

01 · Security

Checks before anything ships

Scans dependencies for known vulnerabilities, scans for leaked secrets, and blocks the build if a real .env file or a service-role key ever gets committed.

job: security
02 · Evals & guardrails

The QA pass, automated

Typechecks, lints, builds, then drives a headless browser through all 6 routes — fails on any crash, blank page, or uncaught error. The same check run by hand before, now on every push.

job: evals
03 · Deployment

Ships to the right place

Only runs if the two above pass. Reads which branch triggered the run and deploys to that environment's Vercel project — dev, qa, or the real, public site.

job: deploy

Get a Vercel token

1 min

vercel.com/account/tokens → Create Token → name it github-actions → copy it.

Grab the org ID and three project IDs

2 min

After npx vercel links a folder, open .vercel/project.json in it:

{ "orgId": "team_xxxxxxxx", "projectId": "prj_xxxxxxxx" }

orgId is the same in all three folders — grab it once. projectId is different for each of the three — grab all three.

Add 5 secrets to GitHub

2 min

Repo → Settings → Secrets and variables → Actions → New repository secret:

SecretValue
VERCEL_TOKENthe token from step 1
VERCEL_ORG_IDthe shared orgId
VERCEL_PROJECT_ID_DEVprojectId for apex-badminton-dev
VERCEL_PROJECT_ID_QAprojectId for apex-badminton-qa
VERCEL_PROJECT_ID_PRODprojectId for apexclubj

No Supabase key belongs here — the pipeline pulls those straight from each Vercel project's own settings.

Turn on branch protection

optional, recommended

Settings → Branches → Add rule for main → require status checks security and evals to pass before merging. Now a failing agent can physically block a merge.

Push the pipeline itself

one commit

Copy .github/workflows/pipeline.yml, scripts/smoke-test.mjs, and the updated package.json into all three folders (or merge main down into qa and dev), commit, push. All three branches need it to run their own checks.
